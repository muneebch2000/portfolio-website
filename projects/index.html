02 / project roadmap

Build the evidence.
Show the security work.

Eight practical project plans for AppSec, AI security, threat modeling, offensive security, cloud, and network roles. Start with the first three, then deepen the areas you want to specialize in.

Planned work—not completed case studies. Repositories, reports, screenshots, and measured results will be attached after each project is finished.
8 planned projects
01 / start herePlanned

Full-stack AppSec assessment & remediation

Build a small multi-user application, then show the complete path from threat model and testing to verified security fixes.

FastAPI or Node.jsPostgreSQLBurp / ZAPASVSWSTG
Build plan & deliverables

Build sequence

  1. Create roles, tenant-owned records, file uploads, and a REST API in a local lab.
  2. Define security requirements; test authorization, session handling, injection, SSRF, and business logic.
  3. Review relevant source-to-sink flows and fix confirmed issues.
  4. Add negative security tests and show the same test failing before the fix and passing afterward.

Publish when complete

  • Architecture and threat model
  • Assessment report with prioritized findings
  • Fix commits and regression tests
  • Short demonstration and retest summary

Completion criteria: Done when every reported finding includes evidence, a fix or justified decision, and a retest.

Best first project for AppSec: demonstrates assessment, communication, and engineering remediation in one story.

02 / delivery securityPlanned

DevSecOps pipeline with meaningful security gates

Extend the first project with automated checks that developers can understand and act on.

GitHub ActionsSemgrepTrivyGitleaksOWASP ZAP
Build plan & deliverables

Build sequence

  1. Run code, dependency, container, and secret checks against a controlled sample repository.
  2. Map representative findings to real code and assess false positives.
  3. Define severity thresholds and an exception process with expiry and ownership.
  4. Demonstrate a pull request blocked by a genuine issue and accepted after remediation.

Publish when complete

  • Workflow and documented gates
  • Custom rule or tuning examples
  • SBOM and scan summaries
  • Evidence of blocked and repaired builds

Completion criteria: Done when the pipeline catches a seeded issue, produces useful guidance, and passes after a verified fix.

Shows that you can make security part of delivery, rather than only producing scanner output.

03 / AI flagshipPlanned

Secure multi-tenant RAG assistant

Build and assess a retrieval application with identity-aware document access, untrusted content, and measurable defenses.

Python / FastAPIOllama or hosted LLMFAISS / ChromaPyRIT or garakDocker
Build plan & deliverables

Build sequence

  1. Use synthetic documents assigned to separate users or organizations.
  2. Test indirect prompt injection, cross-tenant retrieval, leakage, and unsafe output handling.
  3. Enforce document authorization outside the model; record source provenance and sanitize downstream output.
  4. Compare baseline and defended behavior on a fixed test set with a documented scoring rubric.

Publish when complete

  • Data flow diagram and threat register
  • Reproducible test dataset
  • Evaluation report with failures and limitations
  • Defense implementation and regression tests

Completion criteria: Done when access boundaries are independently tested and results distinguish model behavior from application enforcement.

Combines AppSec, AI evaluation, data protection, and secure architecture.

04 / agent securityPlanned

Agent tool-permission testbed

Create an agent with mock tools and test whether untrusted instructions can cause unauthorized actions.

PythonMock APIs / MCP serverScoped identitiesAudit logs
Build plan & deliverables

Build sequence

  1. Provide read-only and write-capable tools with explicit permissions.
  2. Test malicious tool responses and attempts to exceed task scope using synthetic data.
  3. Validate authorization and consequential actions outside the model; enforce budgets and sandbox boundaries.
  4. Evaluate containment, denial behavior, and completeness of the audit trail.

Publish when complete

  • Tool policy and permission matrix
  • Attack and defense test cases
  • Action audit examples
  • Containment and incident-response notes

Completion criteria: Done when denied actions remain blocked despite model output and every attempted action is attributable.

Demonstrates practical controls for tool-using AI systems.

05 / secure designPlanned

Threat model for a cloud-hosted AI application

Design an application threat model spanning browser, API, identities, retrieval, model provider, tools, and cloud services.

OWASP Threat DragonSTRIDEAttack treesASVSOWASP GenAI
Build plan & deliverables

Build sequence

  1. Draw data flows and distinguish trust boundaries and privileged operations.
  2. Document realistic abuse cases and the assumptions behind each threat.
  3. Prioritize risks and assign mitigations, control owners, and verification methods.
  4. Review the design again after adding an agent tool or another tenant.

Publish when complete

  • Versioned diagrams
  • Threat register
  • Security requirements
  • Review notes and residual-risk decisions

Completion criteria: Done when each high-priority threat maps to a specific control and a testable verification step.

A strong companion to the RAG project that demonstrates architecture reasoning.

06 / offensive labPlanned

End-to-end internal assessment lab

Create an isolated Windows and Linux environment and document an OSCP-style assessment from discovery through remediation.

Kali LinuxWindows / Active DirectoryNmapBloodHoundPowerShell
Build plan & deliverables

Build sequence

  1. Define scope and build an isolated lab using deliberately configured weaknesses.
  2. Enumerate hosts, services, identity relationships, and potential escalation paths.
  3. Validate a controlled attack chain with reproducible evidence and an activity timeline.
  4. Harden the exposed configuration, clean up test artifacts, and retest the original path.

Publish when complete

  • Lab topology and scope
  • Technical and executive reports
  • Attack-path evidence
  • Hardening changes and retest results

Completion criteria: Done when another practitioner can reproduce the lab and verify that the repaired attack path is blocked.

Connects OSCP skills to professional assessment and reporting.

07 / cloud defensePlanned

Cloud IAM attack-path review & hardening

Review how workload exposure, identity trust, and permissions combine to create risk in a small test account.

AWS IAMTerraformCloudTrailTrivyPython
Build plan & deliverables

Build sequence

  1. Create a narrowly scoped environment with synthetic assets and a budget limit.
  2. Map role trust, permissions, storage exposure, and workload access.
  3. Validate permission assumptions using non-destructive checks.
  4. Reduce privilege, improve logging, and test the corrected policy.

Publish when complete

  • Infrastructure code
  • IAM attack-path diagram
  • Before/after permission review
  • Audit evidence and cleanup procedure

Completion criteria: Done when the intended workload still functions and excess access is demonstrably denied.

Uses your cloud background to show security engineering depth.

08 / network defensePlanned

Segmentation & detection validation lab

Build separate application, administration, and internal-service zones, then verify both connectivity and detection.

LinuxFirewall rulesWiresharkSuricata or Zeek
Build plan & deliverables

Build sequence

  1. Define an access matrix and implement separate network zones.
  2. Validate every allowed flow and representative denied paths.
  3. Generate controlled test traffic and inspect logs or packet captures.
  4. Tune one detection rule and record its false-positive limitations.

Publish when complete

  • Network diagram
  • Access matrix and rule set
  • Packet and alert evidence
  • Validation report

Completion criteria: Done when segmentation and detection claims are supported by repeatable tests.

Demonstrates network controls with evidence rather than diagrams alone.
